# IntelX — Assurance Scoring Methodology

This document is the authoritative description of how a raw detector signal becomes an
`overall_risk_score` and a `recommended_disposition` (ACCEPT / REVIEW / QUARANTINE). It exists so
that number is never arbitrary from the analyst's point of view: every score can be traced back
through this exact chain to the specific evidence that produced it.

```
Evidence (real bytes: image pixels, model weights, inference records, audit entries)
    ↓
Detector Result (a concrete measurement: a z-score, a digest match/mismatch, an ASR, a hash recalculation)
    ↓
Finding (FindingSchema: severity + confidence + evidence + recommended_action, one per detector hit)
    ↓
Severity Assignment (per-detector threshold on the detector's own measurement)
    ↓
Finding Confidence (a fixed, per-detector-type constant — see "Confidence is not yet dynamic" below)
    ↓
Risk Aggregation (RiskEngine.compute_overall_risk — the ONLY place scores are combined)
    ↓
Overall Assurance Score (0–100) + Recommended Disposition (ACCEPT / REVIEW / QUARANTINE)
```

Source of truth for everything below: `backend/assurance/risk_engine.py` and the individual
detector modules cited per section. This document is generated by reading that code, not the
reverse — if the two ever disagree, the code is correct and this document is stale.

## 1. Evidence → Detector Result

Every detector operates on real bytes it was actually given (image pixels, model weight tensors,
signed inference records, audit-log entries) — never on a synthetic stand-in. A detector's
"result" is one concrete, reproducible measurement:

| Detector | Measurement | File |
|---|---|---|
| Near-duplicate flooding | Perceptual dHash + Hamming-distance cluster size | `backend/data_assurance/duplicate_detector.py` |
| Out-of-distribution insertion | Z-score of color-moment feature distance vs. reference | `backend/data_assurance/ood_detector.py` |
| Label flipping / mislabelling | Declared-vs-inferred label disagreement ratio | `backend/data_assurance/label_analyzer.py` |
| Trigger/poisoning (data-side) | Spatial matched-filter correlation score | `backend/data_assurance/poisoning_detector.py` |
| Model substitution | SHA-256 digest MATCH / MISMATCH / NO_REFERENCE | `backend/model_assurance/fingerprint.py` |
| Parameter distribution anomaly | Weight-tensor kurtosis / variance | `backend/model_assurance/parameter_analyzer.py` |
| Behavioural anomaly | Reference-vs-candidate prediction divergence rate | `backend/model_assurance/behaviour_analyzer.py` |
| Backdoor trigger response | Attack success rate (ASR) on trigger-vs-clean probes | `backend/model_assurance/backdoor_detector.py` |
| Unknown trigger reconstruction | Neural Cleanse MAD anomaly index on reconstructed mask L1 norm | `backend/model_assurance/trigger_reconstruction.py` |
| Inference tampering | Recomputed hash vs. stored `provenance_hash`/`output_hash` | `backend/provenance/verification.py` |
| Replay / reordering | Nonce reuse / sequence-monotonicity violation | `backend/provenance/verification.py` |
| Audit-log modification | Hash-chain break / signature verification failure | `backend/audit/audit_log.py` |
| Distribution shift | Categorical divergence + pixel-quality delta + embedding Fréchet distance | `backend/drift/distribution_shift.py` |

A detector that lacks the access level or inputs it needs reports `UNAVAILABLE` with a stated
reason at this stage — it never fabricates a measurement. This is the point in the chain where the
"never display an unavailable analysis as a score" rule is enforced: an `UNAVAILABLE` detector
result produces no `FindingSchema` at all, so it can never be silently folded into the aggregate
score below.

## 2. Detector Result → Severity

Each detector maps its own measurement to one of four severities (`LOW` / `MEDIUM` / `HIGH` /
`CRITICAL`) using a threshold specific to that detector — there is deliberately no single unified
formula here, because a "cluster of 8 near-duplicate images" and a "0.42 attack success rate on a
backdoor probe" are not commensurable on the same numeric scale. The actual thresholds in the
codebase today:

| Detector | Severity rule |
|---|---|
| Near-duplicate flooding | `CRITICAL` if cluster size ≥ 8, else `HIGH` (finding only raised at cluster size ≥ 3) |
| OOD insertion | `HIGH` if more than 5 OOD samples found, else `MEDIUM` |
| Label flipping (systematic) | `HIGH` if contributor error rate < 50%, else `CRITICAL` |
| Label flipping (isolated) | `MEDIUM` |
| Trigger/poisoning (data-side) | Always `CRITICAL` |
| Model substitution (digest mismatch) | Always `CRITICAL` |
| Model substitution (no reference declared) | `MEDIUM` (this is a coverage gap, not a confirmed attack) |
| Parameter distribution anomaly | Always `HIGH` (fires when max kurtosis > 8.0 or mean variance > 0.5) |
| Behavioural anomaly | `CRITICAL` if deviation rate > 25%, else `HIGH` |
| Backdoor trigger response | Always `CRITICAL` (fires when ASR ≥ 0.35) |
| Unknown trigger reconstruction | Always `HIGH` (fires when MAD anomaly index ≥ 1.8) |

These thresholds are empirically set, not derived from a formal statistical model — several are
explicitly documented in their own source files as "calibrated against this system's own fixtures,"
most notably the Neural Cleanse MAD threshold. This is stated as a known limitation, not hidden.

## 3. Detector Result → Finding Confidence

**Confidence is not yet dynamic.** Every finding's `confidence` field today is a fixed constant per
detector type — it reflects that detector's general reliability as designed, not a live,
per-instance statistical estimate computed from the specific sample at hand. The actual values in
the codebase:

| Detector | Confidence |
|---|---|
| Model digest mismatch / NO_REFERENCE | 1.00 (a bitwise byte comparison has no ambiguity) |
| Trigger/poisoning (data-side) | 0.98 |
| Backdoor trigger response (behavioural) | 0.97 |
| Near-duplicate flooding | 0.96 |
| Behavioural anomaly | 0.95 |
| Label flipping (systematic) | 0.92 |
| OOD insertion | 0.91 |
| Parameter distribution anomaly | 0.91 |
| Label flipping (isolated) | 0.88 |
| Unknown trigger reconstruction (Neural Cleanse) | 0.75 (explicitly lower — reflects that this is blind reconstruction against a never-specified trigger, a materially harder and less certain claim than matching a known signature) |

This is a real limitation worth stating plainly: two findings of the same type currently carry
identical confidence regardless of how strong the underlying signal was for that specific instance
(e.g., a near-duplicate cluster of 20 images gets the same 0.96 as a cluster of 3). The **evidence
strength** classification shown in the UI (`STRONG` / `MODERATE` / `LIMITED`, derived client-side
from whether the detector's evidence names a real-executed method vs. contributor-declared
metadata) is a separate, complementary signal precisely because `confidence` alone doesn't capture
that distinction. A future iteration could make `confidence` itself a function of sample count,
margin over threshold, and access level; today it is a per-detector-type constant, and this
document says so rather than implying otherwise.

## 4. Findings → Risk Aggregation (the only combination step)

All prior stages produce independent `FindingSchema` objects. Exactly one function combines them:
`RiskEngine.compute_overall_risk` (`backend/assurance/risk_engine.py`).

**Step 1 — empty case.** No findings at all → the score is a fixed **4.2**, disposition **ACCEPT**.
This is a deliberate non-zero floor, not a bug: it signals "assessed and found clean under current
coverage," which is a different claim from "never assessed" (an unopened assessment has no score at
all, not a 0).

**Step 2 — weighted sum.** For every other case:

```
weighted_sum = Σ  SEVERITY_WEIGHT[finding.severity] × finding.confidence
               over every finding in the report

SEVERITY_WEIGHT = { LOW: 5.0, MEDIUM: 18.0, HIGH: 40.0, CRITICAL: 80.0 }

overall_risk_score = clamp(round(weighted_sum, 1), 0.0, 100.0)
```

This is a simple linear model, deliberately: it is auditable by hand (an analyst can recompute it
from the findings list alone) rather than a black-box classifier. The weight ratios (5 : 18 : 40 :
80) mean a single CRITICAL finding at full confidence (80.0) already clears the QUARANTINE
threshold (60.0) on its own, by design — the policy below does not rely on the numeric score alone
to reach that disposition regardless.

**Step 3 — disposition thresholds**, evaluated in this order:

```
QUARANTINE  if  any CRITICAL finding
            OR  ≥ 2 HIGH findings
            OR  overall_risk_score ≥ 60.0

REVIEW      if  exactly 1 HIGH finding
            OR  ≥ 2 MEDIUM findings
            OR  overall_risk_score ≥ 25.0

ACCEPT      otherwise
```

Note the disposition is **not** purely a function of the numeric score — a single CRITICAL finding
forces QUARANTINE even if, hypothetically, its weighted contribution alone were below 60 (it never
is, since CRITICAL × any confidence ≥ ~0.75 already exceeds 60, but the categorical rule is
evaluated independently of that arithmetic coincidence, on purpose). This means the score and the
disposition should always be read together: the disposition is the actual decision, the score is
the continuous signal that explains its magnitude and lets two QUARANTINE results be compared to
each other.

## 5. Policy versioning

`RiskEngine.POLICY_VERSION` (currently `"policy-2026.1"`) is carried in every generated
`AssuranceReport.policy_version` field. Any future change to `SEVERITY_WEIGHTS` or the disposition
thresholds must bump this constant, per the PRD's requirement (§9.3) that a report generated under
one policy can never be silently reinterpreted as having been evaluated under another. A report's
score and disposition are only comparable to another report's if `policy_version` matches.

## 6. What this methodology deliberately does not claim

- It does not claim to be a formally validated statistical risk model — it is a transparent,
  auditable weighted-sum-plus-categorical-override policy, chosen specifically so an analyst can
  hand-verify any score without needing to trust an opaque calculation.
- It does not claim per-instance confidence calibration (see §3) — this is the clearest concrete
  next step for strengthening the methodology's rigor.
- A high score or QUARANTINE disposition is evidence-based risk grading, not proof of malicious
  intent, and not a mathematical guarantee that no undetected issue exists outside this system's
  declared coverage (see `COVERAGE.md`).

## 7. Where this shows up in the product

- `AssessmentResultCard`'s clickable score reveals a live rendering of §4 for that specific report:
  per-category finding counts, the top-severity findings that drove the disposition, and the
  report's own `limitations` list — the UI implementation of "why is this number what it is."
- `FindingsTriage`'s per-finding "Evidence Strength" badge is the UI's attempt to surface exactly
  the gap named in §3 (confidence is fixed per detector type; evidence strength differentiates a
  real-executed detection from a metadata-only fallback within that same confidence value).
